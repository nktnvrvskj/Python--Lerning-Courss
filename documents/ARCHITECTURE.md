# Архитектура «Менеджера задач v0.2.0»

Документ объясняет, как устроен проект, зачем нужен каждый класс и как
ответить на вопросы по любому участку кода.

---

## 1. Принципы

1. **Одна причина для изменения на класс** (SRP):
   * `Task` меняется, если меняются поля задачи;
   * `StorageManager` — если меняется способ хранения;
   * `Interface` — если меняется внешний вид;
   * `TaskManager` — если меняется сценарий работы пользователя.
2. **Зависимости в одну сторону**:
   `main → TaskManager → StorageManager → Task`,
   `main → TaskManager → Interface → App* → tkinter`.
   Обратных импортов нет: `Task` не знает о хранилище, `Interface` не знает о
   задачах, `StorageManager` не знает об окне.
3. **Логика не зависит от GUI**. `TaskManager` не импортирует `tkinter`, поэтому
   его можно тестировать с подставным интерфейсом (так и сделано в
   `tests/test_task_manager.py`).
4. **Ошибки не роняют приложение**: неверный ввод, недоступный файл и битый
   JSON обрабатываются и показываются пользователю.

## 3. `Task` — модель

Файл: [src/task.py](../src/task.py)

```python
@dataclass
class Task:
    title: str
    description: str = ""
    status: bool = False
    author: str = "—"
    created_at: str = field(default_factory=lambda: datetime.now().isoformat(timespec="seconds"))
    id: int | None = None
```

* `@dataclass` автоматически создаёт `__init__`, `__repr__`, `__eq__` — не нужно
  писать их вручную.
* `field(default_factory=...)` нужен, потому что значение по умолчанию
  вычисляется при создании **каждого** объекта (иначе дата была бы общей).
* `id = None` означает «задача ещё не сохранена»; настоящий id выдаёт
  `StorageManager`.

### `__post_init__`

Вызывается автоматически после `__init__`. Приводит данные к типам и проверяет
инвариант: название не пустое. Именно поэтому `Task(title="   ")` выбрасывает
`ValueError`, а `Task.from_dict` вызывается внутри `try/except` в хранилище.

### `to_dict()` / `from_dict()`

```python
task.to_dict()          # Task -> dict (для JSON)
Task.from_dict(data)    # dict (из JSON) -> Task
```

Это граница сериализации: JSON-библиотека не умеет работать с объектами, поэтому
на диск уходят только словари. `from_dict` понимает старый формат v0.1.0:
если нет `title`, но есть `name`, берётся `name`. Статус-строка (`"выполнено"`,
`"true"`, `"1"`) тоже приводится к `bool`.

## 4. `StorageManager` — хранение

Файл: [src/storage_manager.py](../src/storage_manager.py)

```python
def __init__(self, path="tasks.json"):
    self.path = Path(path)
    self._tasks = []
    self.load()
```

Объект хранит **кэш** `_tasks` и путь к файлу. Кэш нужен, чтобы `add/update/
delete` работали с текущим списком, не перечитывая файл на каждую операцию.

### `load()`

1. Если файла нет — создаёт пустой (`save([])`) и возвращает `[]`.
2. Читает файл и разбирает JSON.
3. Если JSON повреждён — копирует файл в `task.json.broken`, пишет пустой список
   и возвращает `[]`. Приложение продолжает работать.
4. Каждую запись превращает в `Task` через `from_dict`; «мусорные» записи
   пропускаются, а не ломают весь список.
5. Чинит id: если id нет или он повторяется — выдаёт следующий свободный.
6. Если что-то исправилось, сразу сохраняет файл (миграция старого формата).

### `save(tasks)`

```python
tmp_path = self.path.with_name(self.path.name + ".tmp")
tmp_path.write_text(json.dumps(...))
tmp_path.replace(self.path)
```

Запись сначала идёт во временный файл и только потом заменяет основной. Если
приложение упадёт посреди записи, старый `task.json` останется целым — это
называется атомарной записью.

### `add` / `update` / `delete`

* `add` — если id нет или занят, вызывает `_next_id()` (`max(id) + 1`),
  добавляет задачу и сохраняет.
* `update` — ищет по id, подменяет объект, сохраняет; если id не найден,
  выбрасывает `StorageError`.
* `delete` — удаляет по id и возвращает `True/False` (нашли или нет).
* `get` — вспомогательный поиск для тестов и отладки.

## 5. Компоненты `App*`

Файлы: [src/ui/Button.py](../src/ui/Button.py),
[src/ui/Entry.py](../src/ui/Entry.py), [src/ui/Label.py](../src/ui/Label.py),
[src/ui/Listbox.py](../src/ui/Listbox.py), [src/ui/Frame.py](../src/ui/Frame.py),

Каждый класс — наследник соответствующего tk-виджета:

| Класс | Наследник | Особенности |
|:--|:--|:--|
| `AppFrame` | `tk.Frame` | фон панели, без рамки |
| `AppLabel` | `tk.Label` | единый шрифт, цвет, `set_text()` |
| `AppEntry` | `tk.Entry` | однострочное поле, `get_value/set_value/clear_value` |
| `AppText` | `tk.Text` | многострочное описание, те же методы |
| `AppButton` | `tk.Button` | варианты `primary/secondary/danger` |
| `AppListbox` | `tk.Listbox` | `set_items`, `selected_index`, `select_index` |
| `AppScrollbar` | `tk.Scrollbar` | тонкая полоса прокрутки списка |

Наследование, а не обёртка, выбрано потому, что так компоненты остаются
настоящими tk-виджетами: их можно паковать, гридовать, привязывать события.
Интерфейс не обращается к «голому» `tk.Button` и не повторяет цвета в каждом
месте — всё в [src/ui/theme.py](../src/ui/theme.py).

## 6. `Interface` — прослойка к tkinter

Файл: [src/ui/Interface.py](../src/ui/Interface.py)

Задача класса — быть **единственным** местом, где `TaskManager` встречается с
окном. Он не импортирует `Task` и не решает, что делать с данными.

### Жизненный цикл

* `__init__` создаёт `tk.Tk()`, задаёт заголовок, размер, иконку. Виджеты пока
  не создаются.
* `build()` собирает окно из трёх зон: сверху — список и карточка
  подробностей, ниже — форма, ещё ниже — кнопки и статус-строка. Повторный
  вызов игнорируется (`_built`), чтобы нельзя было построить два окна поверх
  друг друга.
* Стиль намеренно простой: светлый фон, белые карточки, тонкие рамки, один
  акцентный синий цвет. Все значения — в `ui/theme.py`.
* `run()` — `root.mainloop()`.
* `quit()` — `root.destroy()`.

### Как кнопки связаны с логикой

`Interface` не знает методов `TaskManager`. Он хранит словарь действий:

```python
interface.set_actions({
    "new": task_manager.start_new_task,
    "save": task_manager.save_task,
    "delete": task_manager.delete_task,
    "toggle": task_manager.toggle_status,
    "select": task_manager.select_task,
    "refresh": task_manager.refresh,
    "quit": interface.quit,
})
```

Кнопка вызывает `self._invoke("save")`, а `_invoke` достаёт нужный колбэк.
Это разрывает жёсткую зависимость: `Interface` знает только имена действий.

### Ввод и вывод

* `get_input()` — возвращает `{"title", "description", "author"}`.
* `set_input(task)` — заполняет поля из `Task` или словаря.
* `clear_input()` — очищает форму.
* `show_tasks(tasks)` — рисует компактные строки `✓  Название` (описание в
  списке не дублируется — оно показывается справа).
* `show_task_details(task)` — заполняет правую карточку: название, статус,
  описание, автор, дата создания и ID. При `task=None` показывает подсказку
  «Выберите задачу слева…».
* `show_message` — пишет в статус-строку; `show_warning` — диалог с ошибкой;
  `ask_confirm` — диалог «да/нет».
* `get_selected_index()` — индекс выбранной строки или `None`.
* `clear_selection()` — снимает выделение (используется кнопкой «＋ Новая»).

`_invoke` ловит исключения и показывает их через `show_warning`, чтобы ошибка в
одном обработчике не убивала главный цикл tkinter.

## 7. `TaskManager` — фасад

Файл: [src/task_manager.py](../src/task_manager.py)

Конструктор принимает зависимости (dependency injection):

```python
def __init__(self, storage=None, interface=None):
    self.storage = storage or StorageManager(NAME_FILES_SAVES)
    self.interface = interface or Interface()
```

Это нужно для тестов: в них передаётся `FakeInterface`, и настоящее окно не
создаётся. В обычном запуске аргументы не передаются — `main.py` просто пишет
`TaskManager()`.

### Методы

* `start_new_task()` — очищает форму и выделение, ставит курсор в название.
* `save_task()` — маршрутизатор: ничего не выбрано → `create_task()`, выбрано →
  `edit_task()`. Именно сюда привязана кнопка «Сохранить» и клавиша Enter.
* `create_task()` — читает форму, проверяет, создаёт `Task`, вызывает
  `storage.add`, обновляет список и карточку подробностей. Форма **не**
  очищается: новая задача остаётся выбранной, и её можно сразу править.
* `edit_task()` — берёт выбранную задачу, читает форму, собирает новую `Task` с
  **тем же** `id`, `created_at` и `status`, вызывает `storage.update`.
* `delete_task()` — спрашивает подтверждение, удаляет по id, обновляет список.
* `toggle_status()` — меняет `status`, сохраняет; при ошибке записи откатывает
  изменение обратно.
* `select_task()` — по индексу списка находит задачу, заполняет форму и
  показывает карточку подробностей.
* `refresh()` — перечитывает файл, обновляет список; если передан
  `select_id`, выделяет задачу и обновляет карточку, иначе показывает
  подсказку вместо подробностей.
* `run()` — передаёт управление `interface.run()`.

### Почему подробности отдельно от формы

Список остаётся коротким и читаемым: в нём только статус и название. Вся
остальная информация (описание, автор, дата, ID) живёт в правой карточке.
Клик по строке — это одно действие `select`, которое и заполняет форму, и
обновляет карточку. Пользователю не нужно открывать отдельное окно или
прокручивать длинные строки.

### Выбор задачи и индексы

В списке строка № `i` соответствует `self.tasks[i]`, потому что
`Interface.show_tasks` вставляет элементы в том же порядке, в котором получил
список. `TaskManager._selected_task()` берёт индекс через интерфейс и
проверяет границы — это защита от устаревшего выделения.

### Валидация

`_read_form()` проверяет:
* название не пустое;
* длина названия ≤ 120, описания ≤ 500, автора ≤ 60.

При нарушении показывается предупреждение и возвращается `None`; вызывающий
метод просто выходит, ничего не сохраняя.

## 8. `main.py` и импорты

```python
SRC_DIR = Path(__file__).resolve().parent
if str(SRC_DIR) not in sys.path:
    sys.path.insert(0, str(SRC_DIR))

from task_manager import TaskManager

def main():
    app = TaskManager()
    app.run()
```

`sys.path` добавляется, чтобы работал запуск `python src/main.py` из любой
папки: остальные модули используют плоские импорты (`from task import Task`),
как было в структуре проекта v0.1.0.

## 9. Последовательности вызовов

### Создание

```text
[Сохранить] → Interface._invoke("save")
            → TaskManager.save_task()
            → (нет выделения) TaskManager.create_task()
            → Interface.get_input()
            → Task(**data) → StorageManager.add(task)
            → save() → task.json
            → refresh() → StorageManager.load() → Interface.show_tasks()
            → Interface.clear_input()
```

### Редактирование

```text
[клик по задаче] → Interface._on_select → TaskManager.select_task()
                 → Interface.set_input(task)
                 → Interface.show_task_details(task)

[Сохранить] → TaskManager.save_task() → edit_task()
            → _selected_task() → _read_form()
            → Task(id=..., created_at=..., status=...)
            → StorageManager.update(id, task)
            → refresh(select_id=id) → карточка обновлена
            → set_input(updated)
```

### Удаление

```text
[Удалить] → delete_task()
          → _selected_task()
          → Interface.ask_confirm()
          → StorageManager.delete(id)
          → Interface.clear_input()
          → refresh() → show_task_details(None)
```

### Отметка «выполнено»

```text
[Готово] → toggle_status()
         → task.toggle()
         → StorageManager.update(id, task)
         → refresh(select_id=id) → карточка со статусом «Выполнена»
```

## 10. Обработка ошибок

| Ситуация | Что происходит |
|:--|:--|
| пустое название | `Task.__post_init__` → `ValueError` → предупреждение |
| слишком длинное поле | `TaskManager._read_form` → предупреждение |
| нет выбранной задачи | предупреждение «Сначала выберите задачу» |
| нет прав на запись / диск | `OSError` → `StorageError` → предупреждение |
| битый JSON | копия `task.json.broken`, пустой список, приложение работает |
| id не найден при `update` | `StorageError` |
| удаление несуществующей задачи | возвращается `False`, список обновляется |

## 11. Как расширять

**Добавить поле (например, `deadline`).**
1. Добавить поле в `Task`, в `to_dict`, в `from_dict` (с значением по
   умолчанию для старых файлов).
2. Добавить `AppEntry` в форму и в `get_input` / `set_input` / `clear_input`.
3. Добавить проверку в `_read_form`.
4. Остальные классы менять не нужно.

**Заменить JSON на SQLite.**
Переписать только `StorageManager`, сохранив методы `load/save/add/update/
delete` и тип возвращаемого списка `list[Task]`. `TaskManager` и `Interface`
не изменятся — это и есть смысл прослойки.

**Добавить фильтр.**
Хранить в `Interface` выбранный режим и фильтровать список в `show_tasks` или
в `TaskManager.refresh`, не трогая хранилище.

## 12. Вопросы для защиты

**Зачем четыре класса, а не один?**
Чтобы у каждого была одна ответственность. Изменение внешнего вида не ломает
сохранение, замена JSON на БД не требует правок окна, а логику можно тестировать
без tkinter.

**Почему `TaskManager` не импортирует `tkinter`?**
Потому что он работает с абстрактным `Interface`. Это позволяет подставить
`FakeInterface` в тестах и не зависеть от дисплея.

**Что делает `@dataclass`?**
Генерирует `__init__`, `__repr__` и `__eq__` по полям. Мы не пишем ручной
конструктор и не забываем поля.

**Чем `to_dict` отличается от `__dict__`?**
`to_dict` явно перечисляет поля и их порядок — это контракт формата JSON.
Случайные внутренние атрибуты в файл не попадут.

**Почему `from_dict` — `classmethod`?**
Ему нужен класс `cls`, а не готовый объект: он создаёт новый экземпляр.

**Почему id присваивает хранилище, а не `Task`?**
Модель не должна знать, сколько задач уже сохранено. Уникальность — забота
хранилища.

**Как получается новый id?**
`max(существующих id) + 1`, начиная с 1. При загрузке дубли и пропуски
исправляются.

**Зачем временный файл при сохранении?**
Чтобы не потерять данные при аварийном завершении: основной файл заменяется
только после успешной записи временного.

**Что будет, если `task.json` содержит мусор?**
`json.JSONDecodeError` перехватывается, файл копируется в `.broken`, создаётся
пустой список. Приложение не падает.

**Как кнопка вызывает нужный метод?**
Через словарь `actions` и `Interface._invoke(name)`. `Interface` не знает
`TaskManager`, а только имена действий.

**Почему `save_task` — отдельный метод, если есть `create_task` и `edit_task`?**
Чтобы кнопка «Сохранить» работала в обоих сценариях: новая задача или
редактирование выбранной. Маршрутизация — тоже логика фасада.

**Как сохраняется статус при редактировании?**
`edit_task` создаёт новую `Task` и явно переносит `status` и `created_at` из
выбранной задачи, поэтому редактирование текста не сбрасывает «выполнено».

**Почему список и форма не расходятся?**
После каждого изменения вызывается `refresh()`, который перечитывает файл и
заново рисует список. Источник истины — файл, а не виджет.

**Почему после создания форма не очищается?**
Новая задача сразу выделяется, и её данные остаются в форме. Если нажать
«Сохранить» ещё раз, это будет редактирование той же задачи, а не создание
дубликата. Для ввода следующей задачи есть «＋ Новая».

**Откуда берётся описание при клике по задаче?**
`<<ListboxSelect>>` вызывает `TaskManager.select_task()`, тот берёт задачу по
индексу списка и передаёт её в `Interface.show_task_details()`. Карточка
обновляет пять подписей; в списке описания нет, поэтому строки короткие.

**Почему описание редактируется в `AppText`, а не в `AppEntry`?**
`tk.Text` поддерживает несколько строк и перенос по словам. Наследник
`AppText` даёт тот же интерфейс `get_value/set_value/clear_value`, поэтому
`TaskManager` не знает, какой именно виджет используется.

**Как протестировать логику без окна?**
Передать в `TaskManager` `FakeInterface` и временный `StorageManager`; пример —
`tests/test_task_manager.py`.

## 13. Известные ограничения
